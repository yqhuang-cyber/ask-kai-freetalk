# Pi 接入任务清单

2026-10-15 · 只排任务，未改运行代码、依赖、学习者数据或冻结评测。依据当前自由对话实现、[规划到豆包的链路](planning-to-doubao-chain.md)、[Pi 理想设计稿](pi-ideal-tutor-harness-design.md)，以及 pindu `f90fcf98` 把 Pi 收成自己产品能力的做法。

## 1. 两个模型分别怎么接

现在有两条模型调用，用途不同。

| 调用 | 现在怎么走 | 这次 Pi 任务 |
| --- | --- | --- |
| MiniMax-M3 | 开聊前和每一轮各请求一次，要求返回 JSON。地址是 `api.minimax.cn` 的对话补全，关闭思考过程，不使用流式输出。时间到了或结果不合格，就改用规则计划 | **接到 Pi。** 用 Pi 的单次工具循环提交计划。HTTP 仍用现在这套 MiniMax 配置，避免把「换执行循环」和「换 MiniMax 接口」混在一次比较里 |
| 豆包实时全双工 | 一条一直开着的 WebSocket。学生音频持续上传，豆包自己识别并生成文字和语音。计划经校验后，编译进 `session.instructions`，在安全的回复边界用 `session.update` 更新后续输入 | **继续走现有 `packages/provider-doubao`。** Pi 的模型接口是一轮文字请求加工具结果。豆包这条连接还要管音频帧、打断、字幕和回复归属。Pi 仓库里的火山引擎接入是方舟上的文本模型，不是这条 Seeduplex 语音会话 |

已接受的计划仍然由现有编译代码写成豆包指令。Pi 只替换「谁提出这份计划」。普通 Web 继续是 `next_turn_advisory`：新计划可以影响后面的输入，不能据此声称已经开口的那一句使用了它。

若以后改成「先识别成文字，再由文本模型写回复，最后朗读」，那是另一条语音架构，不在本清单里。

## 2. 这一阶段做什么

只给自由对话的初始计划和逐轮计划加一条可关闭的 Pi 路径。默认仍是现在的 MiniMax JSON。主题和 Mission 先不动。

Pi 包只用 `@earendil-works/pi-agent-core` 和 `@earendil-works/pi-ai`，并锁死确切版本。不引入完整的 `pi-coding-agent`。开始写代码前，按所选版本重读停止、自动重试、上下文压缩、`terminate` 和默认工具。pindu 锁的是 1.1.0；本次选定 npm 上的 1.2.0。该版本要求 Node 22.19 或更新，仓库引擎已改为 `>=22.19.0`。

运行限制：

- 会话只放内存，不写 `~/.pi`，不读本仓库的 `AGENTS.md`。
- 不注册读文件、改文件、搜索或命令工具。
- 关掉自动重试和上下文压缩。
- 初始计划用 `submit_conversation_plan`，逐轮计划用 `submit_turn_plan`。每个工具只检查字段形状；目标、来源、权限和策略仍交给现有校验。
- 一次计划只接受一次有效提交，提交后结束这轮推理。
- 修复和工具调用算进现有时限：初始化 15 秒，逐轮 2 秒，并保留现有提交余量。模型忽略停止信号，也不能盖掉已经做出的规则计划。

## 3. 任务

顺序：PI-00 → PI-01 → PI-02 → PI-03 → PI-04。PI-05 依赖 PI-04。PI-06 可以在 PI-04 之后用假响应先做。PI-07 依赖 PI-05 和 PI-06。PI-08 依赖 PI-07。未到 PI-08，不把 Pi 设为默认。

| ID | 工作与交付 | 主要位置 | 完成时能看到什么 | 怎样退回 |
| --- | --- | --- | --- | --- |
| PI-00 | 写下所选 Pi 版本、提交或包锁、Node 要求，以及该版本的停止、重试、压缩、`terminate`、默认工具。记下当前 JSON 规划、提示词版本，并指向已有 12 案／18 轮结果，不覆盖旧分数 | 本清单的版本记录；必要时改 `package.json` 的 `engines` 说明 | 版本记录可复核；运行路径和依赖仍与改前一致 | 只删记录 |
| PI-01 | 加入锁版本的 `pi-agent-core`、`pi-ai`。测试确认：不读 `AGENTS.md`、不写 `~/.pi`、不带编码工具、会话只在内存、重试和压缩关闭 | `package.json`、`package-lock.json`、新的隔离测试 | `npm run verify` 与 `npm run replay` 通过。默认规划仍是 MiniMax JSON | 移除这两个依赖即回到当前锁文件 |
| PI-02 | 用现有 MiniMax 配置实现 Pi 所需的模型请求：同一地址白名单、关闭思考、非流式、现有长度上限、可取消、过大响应拒绝 | `packages/provider-minimax/` | 假服务器测试覆盖成功、取消、超时、坏 JSON 和超长响应。不发真实请求 | 不注册这条请求函数即可 |
| PI-03 | 实现两个提交工具和 `planConversation`／`planTurn`。工具内只做形状和重复项检查；业务判断仍调用现有校验。第二次提交无效。提交后结束循环 | `packages/agent-core/` 新适配器；`configuredPlanner` 增加显式选项 | 现有规划测试继续通过。新测试证明缺字段、重复提交和校验失败不会被当成模型计划已接受 | 不选择该选项时走原 JSON 规划 |
| PI-04 | 把 Pi 的工具调用和最多一次修复放进现有 `boundedProposal` 时限。过期、取消和新的学生输入会使结果失效 | `planner-port.js`、`planning-state.js` 的现有时限；新增 Pi 时限测试 | 初始化 15 秒、逐轮 2 秒的原有案例仍成立。迟到工具结果不能盖掉规则计划 | Pi 适配器内部退回；时限数字不放宽 |
| PI-05 | 用显式配置把自由对话的初始计划和逐轮计划切到 Pi。输入快照、资料读取、页面和豆包指令编译保持不变 | 网关的规划配置；自由对话准备与逐轮路径 | 关闭配置时行为与现在一致。打开后仍不读取课程或 Topic Pack。豆包协议测试不需要修改 | 环境配置改回 `minimax` |
| PI-06 | 为冻结的 12 案／18 轮增加离线对照记录。分组是：当前 JSON，以及 Pi 循环加上同一套 MiniMax 请求。规则计划不计入模型接受率 | `scripts/` 或现有 `eval:planning` 的元数据 | 无网络测试能区分格式合格、业务校验通过、降级原因和取消。不保存模型原文 | 对照脚本独立，不改变默认评测分数 |
| PI-07 | 在明确打开真实请求时，各跑一遍这 12 案／18 轮。分开记录接受率、P50／P95、降级率、取消隔离、token 和费用 | 新的结果记录，放在 `docs/eval-results/`，不含原文和密钥 | 两组使用同一输入和同一 MiniMax HTTP。语义问题另作审阅，不把规则降级算成成功。不调用豆包，不做浏览器听感 | 结果只是记录；默认配置不变 |
| PI-08 | 根据 PI-07 写决定：继续试验、保持可选，或移除 Pi 路径 | 本清单和实现记录 | 决定写明证据和未验证项。未决定前默认仍是 JSON | 删除可选路径和依赖 |

每一项改到运行代码时，运行 `npm run verify` 和 `npm run replay`。真实 MiniMax、真实豆包和浏览器听感分开记录。合成回放通过不算语音或教学质量通过。

## 4. 对照时怎么计

两组比较使用已有的 12 个虚构案例、18 轮，以及各自的真实时限。期望答案和未来输入不进入模型请求。

| 指标 | 怎么计 |
| --- | --- |
| 格式合格 | 工具参数或 JSON 能被读成对象 |
| 业务接受 | 通过现有初始化或逐轮校验，并在时限内提交 |
| 模型接受率 | 只计 `planner_kind=llm`。规则计划进入降级分母 |
| 耗时 | 从输入被接受到计划提交或放弃，报 P50／P95 |
| 降级 | 超时、校验失败、服务不可用分开计 |
| 取消隔离 | 停止后返回的结果不能变成已接受计划 |
| 费用 | 计入工具定义带来的输入 token，不只计输出 |
| 语义 | 沿用已有审阅问题：一句话两问、把困难记成已练习、露出内部目标编号。工具提交本身不算语义合格 |

Pi 自带的 MiniMax 接入使用另一套地址和报文。它不进入 PI-07。若 PI-08 决定保留 Pi 循环，再单开一次「同一循环、不同 MiniMax 接口」的比较。

## 5. 这一阶段先不做

- 不把豆包的建连、音频、打断、字幕或 `session.update` 移进 Pi。
- 不打开 `controlled`，也不把本轮语音先规划再生成算进完成条件。
- 不把 `kai-communication-v2`、Topic Pack 或 Pi 的 `SKILL.md` 合并。交流能力清单仍是代码里的固定目录；Topic Pack 仍是已发布的只读课程资料。
- 不启用 Pi 的会话历史树、自动发现技能、长期记忆或可恢复后台任务。
- 不把 Pi 自带的编码代理默认工具、默认会话目录或本仓库 `AGENTS.md` 交给规划模型。
