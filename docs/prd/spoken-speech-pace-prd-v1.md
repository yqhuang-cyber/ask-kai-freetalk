# Agent 口头调速 PRD

版本：1.0　日期：2026-10-25

状态：基于 Ask Kai POC 已实现行为整理的独立产品基线；用于评审、复用和目标项目验收。

适用范围：具备实时语音交流能力的 Agent。本文使用“Agent”表示对话角色；角色可以是 Kai，也可以是目标项目中的其他名称。

相关文档：[需求、技术、实施与移植说明](../spoken-speech-pace-feature-summary.md)。本 PRD 不改变 Ask Kai 当前独立 POC 的业务和授权边界。

## 1. 背景与目标

学习者在交流中会遇到语速过快、过慢或需要恢复常速的情况。产品应让学习者直接口头调整，无需结束对话，并提供与实际执行结果一致的反馈。

目标为：正确识别明确请求，在当前会话中改变后续语音速度，说明正在处理和处理结果，同时保持当前话题和用户控制权。

本功能不自动评估学习能力，不把请求记为学习困难或掌握证据，也不把一次调速自动保存成长期画像。

## 2. 使用场景与核心流程

### 2.1 放慢语速

| 顺序 | 用户或系统行为 |
| --- | --- |
| 1 | 学习者说：“慢一点。” |
| 2 | Agent 以当前速度回应：“好的，我来把语速放慢一点。” |
| 3 | 第一段语音和字幕播放完成后，系统提交新语速，并等待语音服务确认 |
| 4 | 确认成功后，Agent 用新语速说：“已经放慢了，接下来我会说慢一点。” |
| 5 | 后续交流使用新语速，保留原话题和教学目标 |

### 2.2 加快与恢复正常

“快一点”采用相同流程，文案明确为“加快／说快一点”。“恢复正常语速”回到产品定义的正常档，文案明确为“恢复正常”。

两段确认承担不同职责。第一段只确认请求，第二段只在配置确认成功后说明已执行。确认词句可以依角色和语言本地化，两个阶段的事实含义应保持一致。

## 3. 范围

| 本版包含 | 本版不包含 |
| --- | --- |
| 口头明确要求放慢、加快和恢复正常 | 自动根据能力或情绪推测语速 |
| 相对逐档调整与上下限 | 任意精确倍速／参数值的口头设置 |
| 本场会话持续生效 | 单句临时速度或跨会话自动保存 |
| 两阶段确认、状态展示、失败反馈 | 修改词汇难度、回答长度或教学内容 |
| 新输入、打断、退出与迟到结果处理 | 会中下拉框调速及其他手动入口 |
| 与现有语言支架保持一致 | 任意自然语言表达的完整语义理解 |

目标项目若需要扩展范围，应增加独立需求和验证，不默认继承为本版已实现能力。

## 4. 功能需求

| ID | 需求 | 验收条件 |
| --- | --- | --- |
| SP-R01 | 接受明确口头调速请求 | 已接受的“慢一点／快一点／恢复正常”完整输入触发对应动作；同一输入只执行一次 |
| SP-R02 | 保守处理其他表达 | 否定、引用、词义讨论及方向不明的表达不直接改变速度；未识别表达继续普通交流 |
| SP-R03 | 明确回应调整方向 | 第一段确认说明放慢、加快或恢复正常；不提前说已完成 |
| SP-R04 | 逐档调整 | 慢／快一次移动一档；恢复正常回到正常档；范围外请求不越界 |
| SP-R05 | 保持会话范围 | 有效速度用于本场后续回复；不自动写长期偏好；新会话重新采用其默认设置 |
| SP-R06 | 等待第一段播放完成 | 未完成音频排空和字幕展示时，不推进到更新阶段；暂停播放会阻止提前推进 |
| SP-R07 | 使用实际执行结果 | 配置确认成功后才生成“已调整”确认；失败、超时或不匹配回执不能触发成功文案 |
| SP-R08 | 用新语速说明结果 | 第二段确认使用已更新的语音配置；后续上下文编译继续使用该有效设置 |
| SP-R09 | 保持话题和业务状态 | 单纯调速不新增教学任务、不改写原目标，也不凭控制确认产生学习成果记录 |
| SP-R10 | 响应更新的输入 | 新输入、手动打断、退出或断开使过期确认失效；迟到结果不能在后续轮次重新播出 |
| SP-R11 | 处理连续请求 | 连续“再快一点／再慢一点”从最新目标继续计算；在途更新串行处理，不被旧反馈覆盖 |
| SP-R12 | 说明速度边界 | 已在最快／最慢／正常目标时，说明当前状态；没有实际变化时不声称又调整了一档 |
| SP-R13 | 显示真实状态 | 客户端区分正在处理、上次确认速度、完成和失败，不把目标值当成已生效值 |
| SP-R14 | 遵守语言策略 | 确认语采用当前角色和语言策略；Ask Kai 中文优先，需要时加短英文 |
| SP-R15 | 保持权限和记录边界 | 仅控制当前已授权会话；不把学习者数据、密钥或录音用于无关诊断或跨项目移植 |

SP-R01 的识别范围以已验证表达为准。本版使用有限规则，未声称覆盖所有同义表达、口音或转写错误。

## 5. 速度和作用范围

### 5.1 产品语义

产品定义一组有序速度档。初始档来自目标项目允许的默认设置；本场最新明确请求优先于旧画像和初始计划。后续 Planner 或资料刷新不得静默恢复旧语速。

“恢复正常”表示回到正常档，不表示恢复为开聊时选择的慢速档。

### 5.2 Ask Kai 当前配置

| 档位 | 当前豆包参数 |
| --- | ---: |
| 更慢 | -40 |
| 慢速 | -20 |
| 正常 | 0 |
| 较快 | 20 |
| 更快 | 40 |

开聊前仍保留慢速／正常两种默认选择。会中通过口头请求在五档之间移动，每次一步 20。这是当前供应商的参数映射，不是通用速度单位或固定百分比。

移植时允许更换数值映射，但应保留逐档调整、边界反馈和正常档语义，并重新验证清晰度。

## 6. 状态、取消与异常

### 6.1 产品状态

客户端应能表达：收到请求、正在确认、等待配置、已确认新速度、正在播报结果、完成、取消或失败。技术实现可细分内部状态，但不应把内部版本号或供应商事件名展示给学习者。

已有音频不会被追溯变速。系统在可控制的回复边界切换，第一段确认通常仍是旧速度，第二段及后续语音采用新设置。

### 6.2 必须区分的结果

| 情况 | 产品行为 |
| --- | --- |
| 请求未识别 | 按普通交流处理，不宣称速度发生变化 |
| 明确达到边界 | 说明当前已是可用的边界档位 |
| 新输入发生在更新释放前 | 取消旧反馈；未提交的目标不继续执行 |
| 新输入发生在更新发出后 | 不再播过期成功确认；实际有效速度依据在途配置的真实最终结果记录 |
| 播放被暂停 | 等待恢复或明确失败，不伪造播放完成 |
| 用户静音 | 可报告明确标记的静音播放完成；不能宣称用户已听到 |
| 配置／语音／播放等待失败 | 清楚提示未完成，不说“已经调整”；按项目确定的故障策略处理 |
| 退出、授权撤销或断开 | 终止事务；旧回执不得作用于新会话 |

Ask Kai 当前遇到调速、更新或播放等待失败时，沿用明确提示并关闭失败会话的策略。目标项目若采用重试或保留会话，必须另行定义状态恢复和验收条件。

## 7. 与系统其他能力的关系

调速由宿主持有可追踪状态，并通过供应商接口执行。模型的“我会慢一点”不单独作为成功依据。

自动回复、教学上下文更新和取消操作需要协调顺序。调速确认不应与另一段普通回复重叠；错误回复归属不能导致取消新一轮输出。

配置确认只说明语音服务接受了相应配置；客户端播放确认只说明本机播放流程完成。两者都不证明学习者理解了内容，也不构成学习能力或人工交付证据。

## 8. 验收场景

| ID | 场景 | 预期 |
| --- | --- | --- |
| SP-A01 | 正常交流中说“慢一点” | 第一段确认→播放完成→配置确认→新速度结果确认，顺序正确 |
| SP-A02 | 说“快一点” | 目标加快一档，结果方向正确 |
| SP-A03 | 调整后说“恢复正常语速” | 回到正常档；不恢复为初始慢速档 |
| SP-A04 | 连续多个独立输入说“再快一点” | 从最新目标继续步进，不重复应用旧请求 |
| SP-A05 | 已在最慢／最快档继续要求变化 | 不越界，明确说明限制 |
| SP-A06 | 否定、引用、词义问题 | 不因出现关键词就改变速度 |
| SP-A07 | ASR 中间结果和重复完整结果 | 中间结果不执行，同一来源输入不重复执行 |
| SP-A08 | 原自动回复比完整转写更早开始 | 归属和打断正确，不与控制确认竞争输出 |
| SP-A09 | 第一段确认期间暂停／恢复播放 | 暂停时不更新，恢复并完成后继续 |
| SP-A10 | 更新确认被延迟、重复或无法匹配 | 不错认其他更新，不提前播报成功 |
| SP-A11 | 调整期间插话、换题或手动打断 | 旧确认停止；在途配置按真实结果记录 |
| SP-A12 | 第二段确认期间退出并新建会话 | 旧输出／回执不进入新会话，新会话采用自己的默认档 |
| SP-A13 | 发生新的 Planner 或画像刷新 | 已确认本场速度不被旧值覆盖 |
| SP-A14 | 未收到音频或配置确认，或等待超时 | 显示失败，不把请求当作已完成 |
| SP-A15 | 查询学习记录和小结 | 单纯调速及控制确认没有变成学习尝试或掌握证据 |
| SP-A16 | 实际设备和不同口音 | 识别、清晰度、插话和确认等待可接受，并记录设备条件 |

本表是产品验收矩阵，不表示每项都已在真实设备中完成。部分退出、乱序、边界和竞争场景主要由工程／合成测试覆盖，目标项目应按风险补齐真实供应商和设备检查。

## 9. 验证与放行

验证结果分为三类保存：

1. **工程／合成验证：** 请求判别、状态机、版本、归属、连续请求、边界、错误和迟到隔离。
2. **真实供应商验证：** 作者语音请求、实际配置确认、实际返回音频，以及调速参数的效果对照。
3. **客户端与真人体验验证：** PCM／字幕完成、暂停恢复、实际麦克风、扬声器／耳机、回声及不同口音。

Ask Kai 当前基线为 527 项全量测试通过，其中本功能新增 12 项；三个合成回放、通用及专项 Chromium 检查通过；真实豆包完成同连接三笔作者语音事务。真实探针中的 CLI 播放回执为明确标记的合成静音回执，不能用作真人播放证据。标准化真人设备验收仍开放。

目标项目放行前，应分别提供上述三类记录，并明确尚未覆盖的条件。不能只凭 Agent 文案、参数发送记录或合成回放判定真实体验已经通过。

建议记录从完整转写到请求确认开始、从第一段播完到配置确认、整笔事务完成耗时，以及失败、取消和达到边界的比例。具体时延门槛由目标项目结合设备与语音服务实测确定；本版没有已验收的统一毫秒承诺。

## 10. 移植前必须确认的事项

| 项目 | 需要确认的内容 |
| --- | --- |
| 语音服务 | 是否支持会中调速、如何映射档位、更新何时生效 |
| 配置结果 | 能否可靠关联实际更新和确认，怎样隔离迟到 ACK |
| 回复控制 | 能否接管原自动回复并合成两段有身份的固定确认 |
| 客户端 | 能否报告同一回复的播放排空和字幕完成，而非只报告音频下载结束 |
| 会话状态 | 哪个模块持有有效设置，怎样防止旧 Planner／画像覆盖 |
| 故障策略 | 更新、取消、播放失败时关闭还是恢复，如何避免错误成功反馈 |
| 体验和角色 | 角色文案、语言支架、速度范围和确认耗时是否适合目标用户 |

以上能力未确认前，可以进行原型验证；不得把本项目已通过的结果直接当成目标项目的上线结论。
