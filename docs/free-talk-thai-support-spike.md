# Free Talk 中文 → 泰语回复可行性 Spike

日期：2026-10-28。范围只限 Free Talk；教师助教、教师备课、作业执行和报告均不在本次范围。

## 1. 结论

**有条件可行，值得进入 Free Talk 专属原型；尚不能认定现有豆包链路已经具备可交付的泰语语音质量。**

用当前本机已审核的 S2S 配置，仅在隔离实验中更换提示词，固定例句、两种自然聊天和词义求助均返回中文在前、泰文在后的文本，以及完成的非静音音频。额外重复的固定例句和自然聊天也出现相同语言结构。这证明当前账户 / 模型 / 音色能产出这类文本与音频流；尚未确认音频中的泰语是否正确、自然、与文本一致。

官方公开模型列表仍把实时语音的支持语种列为中英文；同一页独立 TTS 2.0 / ICL 2.0 列有泰语。**不能将独立 TTS 的语种表当作现有 S2S 的支持保证。** 有界实测也不能改写供应商保证或推广到其他账户、版本、音色。

建议首先保留现有 S2S，核验可回听样本；只有泰语声音质量与持续对话合格后，才做默认关闭的 Free Talk 中泰入口。如果声音质量不足，再验证独立多语种 TTS / 分段链路。当前没有替换正式中英行为。

## 2. 产品理解与边界

- Kai 仍帮助学生用中文自由聊天；泰语承担原来英文的理解支架，不改成教泰语。
- 保留当前中文优先、按理解需要提供支架、当前明确请求优先及本轮 / 本场 / 已授权画像的作用范围。是否改成“每轮固定双语”是另一个决策，本次不自动改变。
- 首个候选以**学生说中文，Kai 先中文后按需泰语**为边界。学生说泰语、泰中混说或泰语口头控制，需要独立验证；不能由输出能力推断输入能力。
- 不增加课程、Topic Pack、必做目标、自动掌握或教师助教依赖。身份和偏好仍在获授权的本地 Mock HSKai 边界内。

## 3. 真实服务实验

使用真实 Doubao `SeeduplexProvider`；模型 `1.2.6.1`、音色 `zh_male_xiaotian_jupiter_bigtts`、语速 `-20`。输入由本机系统 TTS 朗读作者虚构句子，按 16 kHz / 20 ms 发送；下行 PCM 24 kHz。

每个案例独立新建会话，不修改本机 profile；沿用现有适配器的话轮 / 回复归属与正常关闭，不编造供应商协议。提示词是最小自由聊天候选，**未使用普通 Agent 的整份提示词，也未连接普通 Gateway / Planner / 页面**。

| 固定中泰例句 | 是 | 中文在前，含泰文，无拉丁词 | 5 / 11 / 0 | 3.935 秒 | 是 |
| 自然聊音乐 | 是 | 中文在前，含泰文，无拉丁词 | 12 / 44 / 0 | 8.226 秒 | 是 |

7 场均观察到真实就绪、一次 ASR final、输入 / 回复归属匹配、非静音音频、回复完成与关闭 ACK。时长为收到的 PCM 样本数计算，**不是响应延迟、泰语段时长或播放完成时间**。

“只用中文”没有附泰文，但 ASR 不完全匹配，且本轮没有保存转写供语义核对，因此只记为观察，不能直接算控制意图验收通过。泰语输入同样不能认定理解成功：final 不是作者泰文，也未核验是否为等义转写；Planner 会依赖这个 final，存在误归属语义的风险。泰语输入暂不纳入可用能力。

追加两场独立复测用于保存人工回听材料：

| 案例 | 汉字 / 泰文字元 / 拉丁词 | PCM 时长 | 状态 |
| --- | --- | --- | --- |
| 固定中泰例句复测 | 5 / 11 / 0 | 3.958 秒 | 采集完整，ASR 完全匹配，待听感核对 |

固定例句输出文字为作者提供的 `我喜欢音乐。 ฉันชอบดนตรี`。音频和对应模型文字仅保存在被忽略的 `.local/thai-support-spike/`，不是已验收示范，不进入学习记录。

这里的“文字表面结构”只检查首个语言字符及文字系统存在，不能证明每句一一对应、无额外问题、翻译准确或音频读对。4 个首轮中泰样本与两场复测都是小样本观察，不能报告成总体成功率。

## 4. 当前工程缺口

| 层 | 已发现的现状 | Free Talk 后续最小改动 |
| --- | --- | --- |
| 语言状态与口头要求 | `packages/agent-core/language-support.js` 使用 `english_support`，规则和识别均针对英文 | 分开“支架开关 / 程度”和“支架语种”，统一本轮、本场与画像优先级；中文开关先支持，泰语命令另验 |
| 完整语音提示词 | `lessons.js`、`reply-policy.js`、`natural-teaching.js` 均有英文要求；`context-snapshot.js` 共同装配 | 为 Free Talk 编译一致的语种配置，覆盖人设、回复、求助、收尾与控制确认；不能只在最后追加“用泰语” |
| 初始化 / 逐轮 Planner | `conversation-initializer.js` 从获授权资料绑定策略；`pi-planner.js` 枚举 `auto/zh/zh_en` | Free Talk 会话配置进入 required strategy、校验、准备指纹和更新流程；模型不能自行改变语种 |
| 偏好与资料契约 | `hskai-bridge/identity.js`、`contracts/planning.js` 不接受中泰枚举 | 首个原型用 Free Talk 专属会话选项；若要跨会话保存，再版本化扩展授权资料，不能把 `zh_en` 偷换成泰语 |
| 字幕 | `caption-phrases.js` 用中文 / 拉丁字计量，整段泰文可能只计 1 单位；拼音层只注中文 | 增加泰语分词 / 渐进节奏核对，保留泰文组合字符，中文继续拼音；渲染支持 Unicode 不等于音频同步已通过 |
| 审计与观测 | `reply-policy.js` 以 Han / Latin 判断中英；diagnostics 只登记英文指标 | 增加泰语计量和目标语种检查，不能把合法泰文当成错误、也不能因为没有英文就算已解释 |
| 小结与词卡 | `summary-directory.js`、`learning-summary.js`、`session-recap.js` 及页面含英文释义 | Free Talk 可见释义随配置选择，区分已审核内容与模型候选；不把“给过泰语解释”写成已理解或掌握 |

这些文件部分由多个场景复用。实现时应保留默认值和现有兼容契约，显式从 Free Talk 注入配置，并做教师助教默认行为差分。**本次没有修改这些共享文件或教师助教基线。**

首个原型可采用 Free Talk 专属 `support_locale: en|th` 与 `support_mode: auto|required|off` 概念；这是设计候选，不是已发布契约。旧 `auto/zh/zh_en` 数据要在兼容层明确解释，未知配置必须拒绝，不能静默退成英文。

## 5. 候选路径与下一步准入

| 路径 | 收益 | 未通过的门槛 | 建议 |
| --- | --- | --- | --- |
| A：现有 S2S 原生中泰 | 保留现有全双工 / 打断 / 音色；本次已有文本与音频样本 | 泰语发音、等义、持续稳定性及供应商支持范围 | **先验证这一条**，不直接设为默认 |
| B：中文 S2S + 翻译 + 独立泰语 TTS | 原中文语音仍走现有链路，泰语使用明确支持它的产品 | 额外延迟、跨音色、中文播放完成后接泰语、新输入时同时取消旧翻译 / TTS、迟到隔离 | A 的声音不合格时独立 Spike；不能直接把两路音频拼上就算完成 |
| C：ASR → 文本模型 → 多语种 TTS | 可控制完整中泰内容及分段；后续可独立选多语种输入 | 端点、打断、延迟、语音连贯性和现有能力迁移 | 较大改造，当前不启动 |

后续顺序：

1. **TH-01 声音与内容门**：泰语熟练者核对这两条真实回听样本，再覆盖日常聊天、求助、数字 / 专名和中泰切换；评发音、自然度、同义和无额外任务。确认当前 S2S 是否有可依赖的泰语支持范围。若失败，再测独立 TTS。
2. **TH-02 Free Talk 专属配置**：默认仍中英；实验选项中泰；统一完整指令和状态，保持自由聊天初始无目标。准备与实际启动必须绑定同一语种配置。教师助教无新依赖。
3. **TH-03 连续对话与取消门**：多轮求助 / 新表达 / 已知表达，本轮只中文后恢复，明确切换本场语种，改口、打断、规划迟到、收尾及新会话恢复；旧响应的泰语尾段不能串入新输入。
4. **TH-04 页面与实机门**：中泰渐进字幕、中文拼音、移动端换行、实际播放和麦克风插话、学习小结；分别报告合成页面、真实 provider、真人设备结果。达到门槛后再决定默认策略。

目前 TH-01～04 均未完成。学生用泰语说话或发出泰语控制指令需新增独立输入验证，不能被上述输出任务隐式包含。
