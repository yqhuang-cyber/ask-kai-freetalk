# 中英文差异化语速：需求分析与 Seeduplex 可行性 Spike

2026-10-25。范围：独立实验与设计建议，未修改线上 Tutor、网关、Planner、口头调速状态机或浏览器。

**第一轮结论：需求合理，但当前 Seeduplex 公开配置没有分语言语速开关；本次 20 个真实 S2S 样本没有观察到这版提示词让中文额外变慢。暂不能承诺用现有原生 S2S 稳定实现。**

后续约束：保持原生实时 S2S，不采用先生成文本再分段合成的方案。后续继续研究 Tutor 身份与语言用途的提示词，见[第二轮实验](bilingual-tutor-prompt-spike.md)。下文分段合成部分仅保留第一次技术分析，已经排除于当前实施方向。

## 需求应该如何定义

学习者在学中文时，需要中文更容易跟上；英文作为解释或支架，保留当前基础速度下的自然节奏。它是**同一 Tutor 按语言采用不同节奏**的要求，也包含一句回复内的中英文切换。

建议把需求拆成两个维度：

- **本场基础语速**：继续由现有“慢一点／快一点／恢复正常”控制。
- **语言相对策略**：在基础速度上，中文额外放慢，英文不额外放慢。整体调速之后，相对策略继续有效。

例如基础速度为当前默认慢档时，英文仍采用该基础速度，中文在此基础上进一步放慢；这里的“英文正常”指不额外放慢，不是强制覆盖学习者已经选择的慢档。中文更慢的幅度尚未由产品确定，实验中“正常七成”只是用于放大可观察差异，不能直接当成产品承诺。

验收不能比较中文的字／秒与英文的词／秒，因为计量单位和语言节奏不同。应分别用**同一句中文相对自己的基线**、**同一句英文相对自己的基线**比较；中文显著变慢，同时英文保持接近原速度，才符合方向。还需听音确认自然度、句内切换、字音是否被不自然地拖长。

语言比例、词汇难度、句子长度与发声速度应分别控制。不能靠少说中文、多停顿或删减内容来代替所需的中文发声节奏。

## 官方接口可以确认什么

本次查阅[官方 Seeduplex 实时语音协议](https://docs.volcengine.com/docs/DoubaoVoice/endtoend-realtime-voice-full-duplex-version?lang=en)，当前实验使用模型 `1.2.6.1`：

- 创建／更新会话包含一个 `session.audio.output.speed`，默认 0，范围 [-50,100]。
- `session.instructions` 用来引导回复内容与音频风格。
- 未在该实时协议中找到按语言分别设置速度、回复内逐段设置速度或输出字词音频时间戳的公开配置。这个发现不等于证明供应商内部绝无相应能力。

[官方产品介绍](https://docs.volcengine.com/docs/DoubaoVoice/ProductOverview-9?lang=zh)说明实时模型可通过自然语言控制语速等声音表现。因此提示词是值得测试的路线，但这不能推出“中文固定慢 30%、英文误差小于 10%”的供应商保证。

其他独立 TTS 产品的 SSML、时间戳或指令字段不能直接套到当前 Seeduplex 会话协议。`session.updated` 也只证明配置得到确认，不能证明模型已经实现分语言节奏。

## 实验方法

独立探针：[probe.js](../scripts/bilingual-speech-pace/probe.js)。默认执行不联网；显式 `--live` 才运行真实供应商实验。

```sh
node scripts/bilingual-speech-pace/probe.js
node --env-file-if-exists=.env scripts/bilingual-speech-pace/probe.js --live
```

使用本机已审核的配置与已有凭据，四个条件各创建一个新会话，避免上一个条件的上下文影响下一个条件：

| 条件 | 会话 speed | 风格指令 |
| --- | ---: | --- |
| neutral_0 | 0 | 两种语言都自然正常，不刻意放慢 |
| differential_0 | 0 | 中文约正常七成，英文维持正常 |
| differential_minus20 | -20 | 同上 |
| neutral_minus20 | -20 | 两种语言都自然正常，不刻意放慢 |

每个条件依次发送作者生成的“请读中文例句／请读英文例句”，各重复两次，再请求先中文后英文的混合回复一次，共 20 个样本。输入用 macOS 本地语音生成，并按真实时间发送 16 kHz PCM；回复由模型自然 S2S 链路生成，**没有使用固定文本 TTS 提交接口**。

中文目标句为“今天下午，我们一起去公园散步，看看树上的小鸟，再聊聊你喜欢的事情。”；英文是对应的固定公园散步例句。通过输出文字完成事件核对内容，排除内容变长导致的假性变慢。文字核对本身不替代听音或独立音频转写。

音频按有归属的回复累计 24 kHz／16-bit 单声道 PCM 字节数换算时长，同时计算去除两端低能量区后的声音跨度，辅助检查尾部静音的影响。能量窗口 10 ms、RMS 阈值 300；这个启发式统计不是词级对齐，也没有把混合回复的音频可靠拆为中文、英文两段。混合回复只能检查完整内容与完整音频生成，不能单凭总时长证明句内分别调速。

每个会话、每条输入和每个回复分别核对身份；不使用无回复归属的 usage 事件判断完成。单次实验上限 480 秒、12,000 个下行事件，每段最多 40 秒输出音频；遇到错误即停止，不无限重试。

作者生成的输入文件和本地统计置于已忽略的 `.local/`；供应商音频、ASR 和回复转写只在内存中处理。没有麦克风、真实学习者数据、原始事件存档、Mock HSKai 交付回执或学习证据写入。

## 实测结果

当前配置为 `1.2.6.1`、音色 `zh_male_xiaotian_jupiter_bigtts`。四个会话全部收到关闭确认；20 个样本全部识别到正确作者请求，输出文字与目标一致，收到有归属的文字和音频完成事件。探针状态 `measured` 只表示采集完成，不代表需求通过。

下面单语言数据为两次测量的中位数，混合数据每个条件仅一次。**同一列内比较**，不要用中文与英文的绝对时长推断哪个语言更快。

| 指令与基础速度 | 中文时长 | 英文时长 | 混合回复总时长 |
| --- | ---: | ---: | ---: |
| 自然节奏，speed=0 | 5.399 s | 7.419 s | 12.175 s |
| 中文额外放慢，speed=0 | 5.297 s | 7.377 s | 12.763 s |
| 中文额外放慢，speed=-20 | 6.752 s | 8.619 s | 16.237 s |
| 自然节奏，speed=-20 | 6.754 s | 8.868 s | 14.960 s |

相同基础参数下，加入“中文约正常七成，英文正常”的指令后：

- speed=0：中文时长相对基线为 0.981 倍，英文为 0.994 倍。中文没有变慢。
- speed=-20：中文时长相对该档基线为 1.000 倍，英文为 0.972 倍。中文仍没有额外变慢。
- 去除两端低能量区后，中文声音跨度分别为 5.225→5.115 秒、6.575→6.540 秒，方向一致，不能用首尾静音解释出所需的中文放慢效果。

反过来，在自然节奏指令不变时，speed 从 0 改为 -20，中文时长约增至 1.251 倍，英文约增至 1.195 倍，符合基础参数影响两种语言的方向。英文单次样本有明显自然波动，不能据此标定精确百分比。

混合回复虽然完整生成，但总时长增加并不证明增加发生在中文部分；本次未做字词对齐或听音验收，不宣称句内语言切换已验证成功。

这是单音色、固定示范内容、每条件单语言各两次的小样本实验，条件顺序固定，没有跨会话重复或统计显著性检验。结果足以说明**这版提示词尚不能作为可靠实现**，不能证明所有音色、所有自然对话或所有提示词都不可能。后续若继续尝试提示词，应单独验证直接口头指定语言节奏、其他措辞、完整 Tutor 上下文和更多混合句型；当前实验输入只要求读例句，没有口头提出差异化调速请求。

| 验证层次 | 本次结果 |
| --- | --- |
| 工程／合成 | `npm run verify`：527／527 通过；`npm run replay`：三个 synthetic 场景完成预期终态。它们不证明声音效果。 |
| 真实供应商 | 四个真实会话、20 个作者语音输入与自然 S2S 输出；收集完毕，差异化语速未得到支持。 |
| 浏览器／人工听音 | 未运行；未验收自然度、实际听感、字幕同步或打断体验。 |

## 接入方案与风险

### 方案 A：保持原生 S2S，通过统一提示词表达语言策略

这是最小改动路线，保留全双工与现有播放链路，但有效性取决于模型的声音指令遵循。只有实验和听音达到要求后，才能作为体验优化接入；不能提供精确比例承诺。

接入时需统一修改初始与会中语速指令的生成入口。现有 `speechPaceInstructions()`、`speechSpeedInstructions()` 是整段“放慢语速”；直接在后面追加“英文正常”会造成冲突，也可能与基础数值速度重复放慢。应让一个版本化策略同时解释基础速度和语言差异，并让后续上下文更新持续保留它。

语言策略与现有口头调速事务共享完整上下文快照和串行配置通道，不另开 `session.update` 通道。确认语只能如实说“接下来中文我会尽量说慢一些，英文保持现在的节奏”；不能仅凭配置 ACK 声称已精确达到某个比例。是否提供按语言的口头调速命令，是后续产品范围，当前保守识别器尚不支持。

现有口头调速的两段确认由宿主固定文本合成，可能包含中英双语；它与本次自然 S2S 示范不是同一生成路径。即使以后自然回复的提示词达标，也需单独验证这些固定确认语的语言节奏，不能推断自动覆盖。

### 已排除的备选：先得到文本，再按语言分段合成

需要更强控制时，可考虑中文段采用较慢参数、英文段采用基础参数，各段开始前等待配置 ACK。这个思路使用现有全局调速能力，但**已经改变直接 S2S 的输出编排**，本次没有实现或验证完整方案。

必须先掌握待朗读文本和语言边界，处理中文句内英文词、人名、缩写、数字和标点，再维护多段音频的统一回复归属、播放回执、打断取消与迟到隔离；还需要验证跨段衔接与首包时延。原生自动回复若已开始生成，不能简单再合成一遍形成重复播报。

### 不建议：看到英文字幕就临时更新会话速度

文字和音频网络事件不提供可靠的字词对齐；字幕到达时，对应音频可能已经生成或进入播放队列。会话更新无法精确定位当前半句话的语言边界，还会与上下文更新、取消和下一轮输入竞争。现有浏览器也依赖原始 PCM 时长完成回执；随意修改播放速度会破坏这项假设。

## 后续实施顺序

1. 保持原生 S2S，继续验证 Tutor 身份、学习者需要和语言用途驱动的提示词；不转向分段合成架构。
2. 明确“中文更慢”的期望幅度以及英文可接受的自然波动；加入短中文、长中文、句内英文词、先英后中、先中后英等样例。
3. 在 Tutor 完整上下文中复测，覆盖初始 slow／normal 与会中调速后的策略保留。独立示范员实验不能替代完整 Agent 验收。
4. 做浏览器听音与打断验证；分别报告合成回归、真实供应商和设备播放结果，再决定接入。
