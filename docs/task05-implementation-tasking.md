## 3. 版本比较与放行规则

### 旧基线和候选

旧 Agent 为 `6661d7ba3ecf7f3eef8f23f74c5d625cb8f457e2`，旧基线清单 `docs/eval-baselines/freechat-v3.1-baseline.json`。现有校验会对改动后的 Agent 报运行文件漂移，05-01 必须新增受控候选契约，不能删除校验或覆盖旧清单。

候选清单采用独立 kind／版本，记录候选提交及父版本、允许的改动文件、完整运行文件哈希、依赖／锁文件、数据／profile原字节哈希、模型／音色／语速、各策略与评分口径，以及输入音频来源和哈希。评测工具提交单独记录。新候选入口必须显式选择候选；该入口和版本清单已由05-01实现，执行说明见[候选评测](candidate-evaluation.md)；历史基线入口继续拒绝漂移。

候选清单绑定已存在的实现提交，清单／报告提交另记，避免用文件内的提交号反向决定包含它的同一提交号。运行前再核对实际工作树、运行文件集合和候选清单；主干仅文档／评测工具后续提交不能冒充新的 Agent 行为版本。

内容变化会改变实际此前 Kai 回复；这是候选行为的一部分，不能用参考前文替换。跨运行前文、模型随机性和供应商状态变化要在报告中列出。Task03 保存 PCM可以按字节复用；旧全量音频未保存的部分，只能保证同作者脚本与已声明合成配置，不能宣称同音频。需要严格比较的重点案可增加同时期旧版／候选对照，但不能覆盖原历史基线。

### 分数和证据

沿用 `kai-content-v3` 十维、权重、0／1／2及 `kai-recorded-review-v2` 校准解释。候选内容仍需独立要求和逐项实际证据；代码自己输出的动作／支架模式不能当正确答案。新总结字段如涉及额外产品覆盖，独立列覆盖与真实性，不暗改历史总结分。

旧 244/255 正式记录、评分及缺口保留；新结果单独编号。Task02／03有效诊断记录不直接补入旧正式全量分数。缺失或不确定项不填通过，不从当前回复倒推识别语义，不将“已转发”当“已听懂”。

每类真评先登记待比较范围与预算，不从重复样本挑最好结果。首轮语言重点对照至少按 Task03 对应条件各两次保留全部结果，这是诊断最小重复数，不构成统计稳定性保证；如结果不一致，再明确追加预算与假设。全量分数不能掩盖新关键失败、明确请求违规或覆盖下降。

### 各类的完成判定

1. 工程合同与受影响测试通过；运行代码／合同变化执行 `npm run verify`、`npm run replay`，涉及 Web 执行 `npm run test:browser`。浏览器合成检查与真实设备验收分开。
2. 指定内容或呈现范围有实际候选记录和同口径复核；关键失败单列。仅工程通过时标“实现完成，真实回归待完成”，不标该类问题已解决。
3. 没有新关键失败或明确硬要求退化。混合改善／退化先记录并复核；不能以平均分增加放行。难以归因时保持待验证。
4. 真实延迟、语速和字幕同步按受影响 Web 场景比较；不在设计阶段捏造毫秒阈值。模型文字符合不等于音频与字幕体验通过。
5. 评审来源明确。模型辅助审查不自动变成人工批准或独立评分模型验证；人工审核未完成继续标记，不阻塞诚实交付实现与证据。
