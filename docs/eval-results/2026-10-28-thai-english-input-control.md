# 中泰 Free Talk：英文输入配对对照

2026-10-28。仅做实验与记录，产品规则、原中英入口、教师助教均未修改。运行标识 `20261028-paired-v1`。

## 结论

**本轮证据支持：英文输入是中泰场景语言偏移的可复现触发因素。普通英文问题已足以触发，不必明确要求“用英语回答”。** 具体表现是把本应出现的中文换成英文，同时保留泰语。不能概括成“只要出现英语就一定失败”：两轮对照显示，先前的中文对话可以维持中泰模式，先前的英文对话也可能让偏移延续到下一轮。

实际中泰入口复核时，服务端仍标记 `support_locale=th`、`support_mode=required`，语音输出却是英泰。问题出现在模型对输出语言的遵循，不能解释成页面进入了中英入口或宿主把支架切成英语。

这些结果说明当前中泰规则对英语输入的抵抗不足；**尚未证明模型内部为什么选择英语，也未通过提示词消融证明某一条指令就是唯一根因。** “多了第三种语言”可描述这一冲突，但不是经过验证的模型内部解释，更不能据此声称所有三语场景都会失败。

## 主对照：固定实际中泰提示，改变输入语言

使用当前 `ThaiFreeTalkSession.instructions()` 组装的真实产品提示，来自获准 Mock 学习者与规则初始计划。固定模型 `1.2.6.1`、音色 `zh_male_xiaotian_jupiter_bigtts`、输出速度 `-20`。所有会话提示 SHA-256 一致：

`9f2fb77cd89b02e88cc92932447b2e1ee543ad8c802739eae01c288fbb90e3f8`

主实验直接经过真实 Seeduplex 适配器，冻结初始提示，不运行逐轮 Planner 或宿主状态更新。这用于隔离语音输入及会话历史的影响，不能冒充完整网关验收。随后另做实际入口复核。

输入为作者编写的游戏、音乐、开心经历三个日常话题，中英文表达相同意思，每个话题重复三次、各用全新会话，形成九组配对。中英文均由同一个豆包音色生成固定朗读素材，再以 16 kHz PCM 实时送入；不是文字注入或真人麦克风。素材在重复会话中复用，三次重复不是三个不同说话人或三种口音。用例和顺序在采集前固定，同一配对最多两场并发。

| 全新会话输入 | 完整回复 | 中文在前、含泰语、无英文 | 英文替代中文 | ASR 与原文一致 |
| --- | ---: | ---: | ---: | ---: |
| 中文 | 9/9 | 9/9 | 0/9 | 9/9 |
| 英文 | 9/9 | 0/9 | 9/9 | 9/9 |

九组配对全部出现“仅英文输入一侧含英文且中文缺失”。这是三个有限话题、一个模型配置下的结果，不是线上故障率估计。

例如问“你最近玩电子游戏吗？”时，回复以“我没办法实际玩游戏……”开头，随后有泰语；换成 `Have you played any video games lately?` 后，回复以 `I don’t have hands to play actual games…` 开头，随后有泰语，未出现中文。此处引用来自作者实验，不是学习者真实记录。本轮复现的是输出语言替换，不声称逐字复现截图中泰文里的 `lately`。

## 多轮：当前输入与历史的作用

八场两轮会话，首轮表达“最近喜欢和朋友聊天”，第二轮询问游戏；四种语言顺序各重复两次。全部输入 ASR 一致。表内统计第二轮。

| 首轮 → 第二轮输入 | 中泰回复 | 英泰回复 |
| --- | ---: | ---: |
| 中文 → 中文 | 2/2 | 0/2 |
| 英文 → 英文 | 0/2 | 2/2 |
| 英文 → 中文 | 1/2 | 1/2 |
| 中文 → 英文 | 2/2 | 0/2 |

因此，当前输入不是独立决定输出语言的开关。先用中文建立对话后，英文问题两次未破坏中泰；先用英文建立对话后，一次改回中文仍延续英泰。这支持会话历史影响的判断，但无法进一步区分先前用户语言与先前模型回复语言各自的贡献，两者在这些会话中共同变化。

另做六场明确要求“只用英语回答”的辅助实验：英文请求三场 ASR 一致，三场均只回复英语，中文与泰语都消失；中文请求三场也均只回复英语，但三场均把“只”识别成“指”，不纳入准确识别的干净对照。普通英文主对照已经复现偏移，因此明确语言变更要求不是必要条件。

## 实际入口复核：中泰与原中英

复用相同游戏、音乐语音素材，分别通过运行中的 4311 中泰入口和 4310 原中英入口完成登录、初始准备、会话、真实语音与结束流程。共八场全新会话，均完整、ASR 一致、回复归属匹配且收到关闭事件。保留实际 MiniMax 初始规划，不冻结提示或规划，因此这组是产品路径确认，不能与主实验合并成完全相同条件的因果样本。

| 实际入口 | 中文输入两场 | 英文输入两场 |
| --- | --- | --- |
| 中泰 4311 | 2/2 中文在前、中泰 | 2/2 英泰，中文缺失 |
| 原中英 4310 | 2/2 中文在前、中英 | 2/2 中文在前、中英 |

四场中泰会话在回复开始前，服务端都仍要求泰语支架；四场初始规划均为真实 LLM、未降级。原中英初始规划亦均为真实 LLM、未降级。这支持“旧入口本轮更稳定”的观察；原中英只有四场复核，不等于所有输入都已验收。

## 代码层面的解释与限制

- **M1 页面**：本轮没有修改。实际入口问题来自收到的模型文本，不能用显示排版解释中文整段消失。
- **M2 网关**：本轮没有修改。中泰回复开始前的状态仍为泰语必需，没有观察到入口或语言状态被切换成英语。
- **M3 Agent**：`packages/free-talk-thai/language.js` 已写“始终先说中文”“不能口头切换中英版”，并按本场/本轮状态生成要求。`packages/free-talk-thai/session.js` 将其放入完整提示；现有审计是诊断，不是播前语言门。主实验冻结这份提示也能复现，故不需要 Planner 更新或状态切换才会发生。
- **M5 语音模型**：同一套提示下，输入和历史改变后，实际输出语言发生变化。现有架构没有强制模型只能生成两种语言的约束。中英与中泰同为提示词驱动，不代表不同语言组合有相同的遵循效果。

提示中“学生新的明确要求优先”等较宽的表述可能需要收窄，但本轮没有修改提示做消融，因此只作为待验证的改进方向。没有声称已经解决问题，也没有实施之前暂停的强制中泰方案。

## 证据与验证

- 真实服务：主实验 32 场 / 40 轮全部完整，37 轮 ASR 一致；其余三轮为上述中文明确英语请求。八场产品复核全部完整。合计 **40 场 / 48 轮**，另有十份输入素材的固定朗读生成。主实验所有回复归属匹配、32 场均获关闭确认。
- 自动文本口径：ASR 一致指 NFKC 规范化后忽略标点、空白与大小写，不修复漏词、同音字或改写。统计汉字、泰文字母、拉丁词及首个文字所属脚本；`expected_surface` 只表示中文在前、含泰语且无拉丁词，不证明逐句等义、语言质量或发音正确。`latin_leakage` 是中泰实验口径；原中英入口有拉丁词是正常表现。
- 工程：`npm run verify` 通过，852 项测试；三类 `npm run replay` 合成回放通过；`npm run check:teacher:isolation` 确认原中英八个受保护文件 hash 未变。没有修改产品运行代码；没有新增浏览器音频或真人听感验收。合成回放结果与真实服务结果分开。
- 安全汇总：[JSON](2026-10-28-thai-english-input-control.json)。只含哈希、计数、配置和状态，不含密钥、原始供应商事件或真实学习者记录。作者输入、私有识别/回复核对文本与素材保留在忽略的 `.local/thai-support-spike/english-control-20261028-paired-v1/`。
- 可复用采集脚本：`scripts/thai-support-spike/english-control/experiment.js`、`gateway-confirmation.js`；统计与固定用例：`cases.js`；统计测试：`tests/thai-english-control.test.js`。真实采集必须显式 `--live` 并指定新的 `--run`，已有完整结果禁止覆盖。
