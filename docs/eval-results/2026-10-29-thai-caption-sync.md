# 中泰字幕与音频同步诊断

2026-10-29。范围：Free Talk 中泰与原中英呈现流程对比。仅新增诊断脚本与记录，没有修改产品字幕、音频、提示词或教师助教代码。工作区中已有其他未提交改动，本轮保持原样。

## 已确认的机制

当前字幕不是使用供应商逐字或逐句时间戳，而是由 **M1 浏览器估算显示时机**。中泰与中英共用 `apps/realtime-gateway/public/presentation.js`、`audio.js`、`caption-annotations.js`；中泰服务器把 `/caption-phrases.js` 映射到自己的泰语分词文件。

`Presentation.advance()` 的规则为：

1. 回复尚在生成时，下一段字幕的播放门槛为“已显示单位 × 300 毫秒”。
2. 回复完成后，门槛改为“整段已接收 PCM 时长 × 已显示单位 / 全部单位”。
3. 两次显示最少相隔 320 毫秒；每 80 毫秒检查一次。未成段文字还有约 400 毫秒软等待。

中泰的 `captionUnits()` 将**一个汉字、一个英语单词、一个泰语分词都算作一个单位**。这不是实际发音时长。尤其长中文接一段泰语时，这些单位的比例会直接决定中文在时间轴上占多长，以及泰文何时才能显示。原中英也使用估算，用户感觉较同步不代表它已经有真实时间戳。

因此可以定位到一个具体、可复现的前端等待机制：文字已经收到，显示器仍因估算的 PCM 门槛而等待。泰语计量没有进行实际语音时长校准，**是本次中泰不同步的主要嫌疑**。尚不能把某个样本“文字收到至显示”的等待秒数等同于它相对对应口语的落后秒数。

## 真实服务对照

固定相同作者中文语音“你最近玩电子游戏吗？”，相同获准 Mock 学习者、音色和实际 Agent 组装提示；初始计划采用规则并冻结，避免 MiniMax 规划变动。中泰使用 `ThaiFreeTalkSession`，原中英使用 `TeachingSession`。正常/慢速各取一场完整回复。直接调用真实 Seeduplex 适配器，不经过常驻网关、不重新启动产品服务。

| 完整样本 | 首段文字比首段音频早到 | 输出 PCM 时长 | 文字收齐时刻 | 首段音频到达时刻 |
| --- | ---: | ---: | ---: | ---: |
| 中泰正常 | 577 ms | 14,990 ms | 6,112 ms | 4,418 ms |
| 中英正常 | 511 ms | 9,578 ms | 4,640 ms | 3,819 ms |
| 中泰慢速补测 | 323 ms | 13,006 ms | 5,073 ms | 3,645 ms |
| 中英慢速补测 | 350 ms | 12,501 ms | 4,627 ms | 3,597 ms |

时刻均从各自连接开始计算，不能跨会话比较绝对启动速度。四场完整样本均 ASR 一致、回复归属匹配、关闭收到确认。中泰两场均含中文与泰文，无拉丁词。

**失败保留：**最初慢速两场分别连接中断、等待完成超时；两场各补测一次后收齐。真实调用合计六次，四次完整、两次失败；不能写成最初四次全部通过。失败不是字幕语义同步结果。

四场完整样本都不是“首段文字比音频晚到”。这支持继续检查前端呈现，不能据此排除其他网络或设备上出现供应商文字迟到。

## 原代码离线重放与浏览器确认

将作者实验中规范化的文字/PCM 字节数/到达时序，重放到原 `Presentation`。Node 重放使用模拟的 PCM 排队时钟，保留实际包间隔、30 ms 音频排队提前量与停顿；不是设备播放验收。

中泰正常样本含 27 个汉字、83 个泰文字母。Node 分段计量合计 45 单位，前面中文占 27 单位，因而完成后的估算把约 `14,990 × 27 / 45 ≈ 8,994 ms` 分给前面的中文。第一段泰文在连接后 13,521 ms 才显示，而全部文字在 6,112 ms 已收到。**这个 8,994 ms 是代码计算出的门槛，并非测得的中文实际朗读时长。**

另在 Chromium 中加载原字幕调度、泰语分词、音频播放与拼音组件，以静音合成 PCM 重放中泰/中英正常样本到达时序：

| 浏览器合成重放 | 文字收齐 | 首段泰文显示 | 最长单次拼音/DOM 绘制 | 页面错误 |
| --- | ---: | ---: | ---: | ---: |
| 中泰 | 2,272 ms | 9,503 ms | 2.2 ms | 0 |
| 中英 | 1,333 ms | 不适用 | 2.1 ms | 0 |

浏览器时刻从本次重放开始计算，已减去原连接前置时间，不能直接与上一表相减。中泰全部文字已收到后约 7,231 ms 才出现首段泰文。绘制开销不支持“拼音渲染本身拖慢数秒”的解释。浏览器与 Node 的分段/计量略有不同，不能把 Node 分词结果当成所有终端的固定时刻。

诊断脚本还在内存中将流式 300 ms 门槛改为零做敏感性对比，产品文件未改变。它只证明显示结果受该门槛影响；取消门槛也会让字幕过早显示，**不是修复方案，差值不是实际字幕滞后量**。

## 结论边界与后续修改方向

- **已确认：**M1 使用粗略文字单位估时；有文字早到但前端继续等待；真实浏览器能复现；这批样本的拼音绘制不是秒级开销。
- **尚未确认：**没有本次用户原始会话时序或逐句参考音频，未测得对应口语与字幕逐句偏差；不能宣称“始终落后 7.2 秒”。不同语言样本的内容、分段和总音频长度也不同，不能只凭展示百分比断定某种语言一定更差。
- **没有新语言规则修复：**先中文后泰语是否遵守，与字幕何时显示是两个问题。本轮中泰样本遵守语言顺序，仍存在上述等待机制。
- **建议的最小范围：**只给中泰入口增加独立的计时适配，保持原中英默认与教师助教不变；先校准中文/泰语的时长权重、分段与语速因素，再用可核对音频测逐句偏差。如取得可靠音频对齐数据，优先绑定句段音频。不能仅调小 80 ms 轮询或把整段字幕立即显示来宣称同步已修复。
